title: Auth

`ratchet/auth` provides session-based authentication (`User`, `Role`, `Session` models, plus a router and pipeline helpers) that `ratchet serve` mounts at `/api/auth`, ahead of the generic `/api/:model` router. A role's entire grant tree lives on the `Role.permissions` json column — there is no separate `Permission` model.

## Endpoints

| Method | Path | |
|---|---|---|
| `GET` | `/api/auth/setup` | whether a root admin still needs to be created |
| `POST` | `/api/auth/setup` | one-time bootstrap: create the root admin |
| `POST` | `/api/auth/register` | create a user, issue a session |
| `POST` | `/api/auth/login` | verify credentials, issue a session |
| `POST` | `/api/auth/logout` | invalidate the current session |
| `GET` | `/api/auth/me` | current user + their permissions |
| `PATCH` | `/api/auth/me` | update your own `email` / `password` |

`setup`, `register`, and `login` all return `{ data: { user, token } }` (setup's `GET` returns `{ data: { required } }` instead) and set an `HttpOnly` session cookie (`Secure` when the request is HTTPS). The console SPA relies on the cookie; non-browser clients can instead send `Authorization: Bearer <token>`.

`PATCH /api/auth/me` is self-service: any signed-in user can change their own `email` and `password` without the `users:update` permission that gates admin-driven edits through `PATCH /api/users/:id`. Only those two keys are honoured — `roleId`, `active`, and everything else are ignored — and the write still runs through the `User` model's own `update` pipeline (`hashPassword` + `validate`). It returns the same `{ data: <user + permissions> }` shape as `GET /me`. The console exposes it as the **Edit profile** page (`/profile`), linked from the account menu in both the sidebar and the workspace header.

## Root admin onboarding

A fresh instance has no users, so `requirePermission` would lock everyone out with no way to grant the first permission. `POST /api/auth/setup` closes that gap: it's unauthenticated, but only works once — it checks whether any user already holds a `*:*` permission (`permissions['*']['*']`) and 409s (`SETUP_ALREADY_COMPLETE`) if so. Otherwise it creates (or reuses) a `Root` role with `permissions: { '*': { '*': { fields: '*', scope: 'any' } } }`, creates the submitted user under that role, and signs them in — the same shape as `register`/`login`.

The same request also provisions the framework's first built-in `Agent`, named `Ratchet`, with `roleId` set to that same `Root` role — so it can call every tool from turn one (see "Agents derive their tools from a `Role`" below). `Agent.providerId` starts out `null`: connecting a Model Provider is a separate step, done from the chat UI's empty-state (or the Providers admin screen) once you're logged in, not part of this form.

The console SPA's `AuthProvider` checks `GET /api/auth/setup` on boot alongside `/me`. While a root admin doesn't yet exist, every console route redirects to its `/setup` route (a form styled like the login page, with a confirm-password field) instead of `/login`; once it's created, `/setup` itself renders a generic not-found page rather than redirecting to `/login`, so a completed instance gives nothing away either.

Root status is keyed off the permission, not user count — a user created through public `/register` (below) has no role and no permissions, so it doesn't count, and `/register` itself is unaffected by whether setup has run.

**In production** (`FrameworkConfig.env` resolving to `'production'`, either set explicitly or inferred from `NODE_ENV`), both `GET` and `POST /api/auth/setup` 404 unconditionally — the same response an unmatched route would produce — so the endpoint never reveals whether a root admin exists. Bootstrap the first admin there with [`ratchet create-admin`](/docs/cli#ratchet-create-admin) instead, which writes directly to the database rather than going over HTTP.

```sh
curl -X POST http://localhost:3000/api/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"a@example.com","password":"hunter2"}'

curl http://localhost:3000/api/auth/me \
  -H 'Authorization: Bearer <token>'
```

## How passwords are handled

The `User` model never declares a plaintext `password` field. Instead its `passwordHash` column declares `writeAs: 'password'`, and the `hashPassword` pipeline function intercepts `ctx.input.password`, hashes it, and rewrites it as `passwordHash` before `validate` runs. `passwordHash` itself is `sensitive: true`, so it's never present in a response.

## Auth + permission is implicit on the generic router

Every route on the generic `/api/:model` router requires a matching permission entry on the user's `Role.permissions` list by default — including reads, which use an implicit `'read'` action (there's no per-model `read` operation to compose a pipeline step into, unlike create/update/remove). A model author doesn't need to do anything to get this; it applies automatically, the same way `redactSensitiveFields` or `?include=` do.

A model that must stay reachable with no session at all (a public read-only catalog, say) opts out with `api: { public: true }`:

```ts
export const Announcement = defineModel('announcements', {
  fields: { /* ... */ },
  api: { public: true },
});
```

`public` applies to every verb on that model — there's no per-operation granularity today.

`requireAuth` and `requirePermission(resource, action)` still exist as ordinary [pipeline functions](/docs/pipelines), for a dedicated router that bypasses the generic one entirely (e.g. `Chat`/`Message`'s own `/api/automation/*` routes, or an agent tool call — `automation/tool.ts`'s `executeAgentTool` calls `authorizeRequest`, the same check under the hood, before ever touching a model's pipeline):

- `requireAuth` resolves the `Bearer` token or session cookie on `ctx.request` to a live, active user and stashes it on `ctx.user`. Throws `UNAUTHENTICATED` (401) otherwise.
- `requirePermission(resource, action)` must run after `requireAuth`. It checks the user's role owns a permission entry matching `(resource, action)` — either side may be granted as `*`. Throws `FORBIDDEN` (403) otherwise, or `UNAUTHENTICATED` if `requireAuth` didn't run first.

## Roles and permissions

`Role` is an ordinary model whose entire grant tree is the `permissions` json column — `Role.permissions` is `{ [resource]: { [action]: { fields?, scope? } } }`, and there's no separate `Permission` model or junction table to manage. Either key may be `'*'` (every resource, or every action on a resource) — but a `'*'` key never coexists with a sibling specific key at the same level: a resource/action grouping is either fully wildcard or fully enumerated, never a mix of both, so the most-specific-match lookup never has to merge two sources of truth. A role's grants are edited through the generic REST API (a `POST /api/roles` create or `PATCH /api/roles/:id` update carrying the whole `permissions` tree) or through the console form (see below) — replacing the entire tree in one call, the same way you'd replace a JSON field on any model.

```ts
// an "Editor" role: full read access to every document, but can only update/delete
// its own — update/remove omit `scope`, so they default to `'own'`
{
  documents: {
    read: { fields: '*', scope: 'any' },
    update: { fields: ['title', 'body'] },
    remove: {},
  },
}
```

`Role`'s console form (`src/auth/models/role.form.tsx`, shipped with the framework — a real, worked example of a [builtin console form](/docs/console#builtin-forms)) edits `name`/`description` the normal way and, in the same form/submit, manages the role's entire `permissions` tree via nested resource/action/field checkboxes (plus an own/any control on a resource with an owner field) where `'*'` collapses a fully-granted subtree into one wildcard key. It persists with a plain `POST`/`PATCH /api/roles`, so it's gated the same "two independent checks" way any role edit is: the `roles:create`/`roles:update` grant from the requesting user's own role, plus the field grants covering the fields being written.

> **Agents derive their tools from a `Role`.** An `Agent` carries a `roleId`, and the tools it may call (`resolveAgentTools`, `src/automation/tool.ts`) are exactly the operations its role's `permissions` grant — so an agent's capabilities are just a role assignment, no separate grant list. A `read` grant yields two builtin read tools per resource, `list_<model>` (filter/sort/offset-pagination, returns `{ data, meta }`) and `findOne_<model>` (one row by id); `create`/`update`/`remove` and custom operations map to a tool each as before. When an agent tool is invoked, the call is additionally gated by the *chatting user's* own role (not the agent's alone) — including the same `read` field grant that scopes a REST response's columns and its `?include=`d relations, and the same `scope` — so an agent can never read or write more than the human driving it already could over `/api/:model`.

## Field-level permission

`fields` names which fields of `resource` a role may read (`action: 'read'`) or write (`action: 'create'`/`'update'`) — `'*'` for every field, or an array of specific field names. It's required on a `read`/`create`/`update`/`'*'` entry and doesn't apply at all to `remove` (which gates a whole row, never individual fields):

```ts
{
  invoices: {
    read: { fields: ['total', 'customerNotes'] },
    update: { fields: '*' },
  },
}
```

This is **secure-by-default, with no implicit "all fields"**: a role with a `(resource, action)` grant but no `fields` gets zero fields for that action, not every field. A read that field permission denies simply omits that key from the response (the same shape `sensitive: true` fields already get); a write that touches a denied field is rejected outright, naming every offending key, rather than silently dropping it. `?filter=`/`?sort=` on a field a role can't read is rejected the same way — otherwise field-read denial would be a trivial oracle to route around.

Two things are always exempt from field-level permission, for every role:

- **Auto-injected system columns** (`id`, `createdAt`, `updatedAt`, `deletedAt`, `createdById`) — they aren't declarable via `field.*` in the first place, and gating them would break pagination cursors, `?include=`, and file-field URLs for no security benefit.
- **`sensitive: true`** fields (e.g. a password hash) — that's a separate, absolute, non-role-based redaction: it never reaches *any* role, whereas field permission is about fields that are fine for some roles but not others.

`?include=`d relations are filtered by the same field grant, using the requesting role's `read` permission on the *related* model — embedding a row via `?include=` can't be used to see fields that model's own permission denies.

## Row-level scope: own vs. any

**Every model has an owner.** By default it's the auto-injected `createdById` system column, which `persistWrite` already force-sets from the requester's id on every insert, for every model, unconditionally — so ownership scoping works out of the box, with no per-model opt-in. A model overrides which field counts as the owner with `api: { ownerField: 'userId' }` (see [Models](/docs/models)) only when the real owner differs from whoever created the row — e.g. `Workspace`'s `userId`, since a self-registered user's default workspace is provisioned with no session at all, so `createdById` would be null there.

`scope` on a grant node controls whether that role sees/writes every row (`'any'`) or only rows it owns (`'own'`) — omitted defaults to `'own'`. Because every model has an owner, **this default applies everywhere**: a role that doesn't mention `scope` at all is restricted to rows it created, on every resource, unless it explicitly grants `scope: 'any'`. `scope` is valid on any resource, including under the `'*'` resource key.

Ownership is entirely role-driven, not baked into a model's pipeline — `create-router.ts` and `automation/tool.ts`'s agent-tool executor both resolve the caller's `scope` for the action being invoked and enforce it automatically (`core/pipeline.ts`'s `ownerFieldOf`/`forceOwnerOnCreate`/`assertOwnsRow`) before a model's own pipeline ever runs. `create` always force-sets the owner to the requester regardless of `scope` — there's no "create on someone else's behalf" capability. A model author never wires an ownership check by hand.

> An "admin" role that should see everything on a resource needs `scope: 'any'` there explicitly — e.g. `{ roles: { update: { fields: '*', scope: 'any' } } }` to let a role manage *any* `Role` row, not just ones it created itself.

### Bootstrapping

Because there's no implicit "all fields," and because every model now defaults to `scope: 'own'`, the Root role `POST /api/auth/setup` creates `permissions: { '*': { '*': { fields: '*', scope: 'any' } } }` — `fields: '*'` and `scope: 'any'` are both what keep the freshly-created admin able to see/edit *anything* immediately (not just rows it happens to have created itself), the same way the `'*'` resource/action keys already do. When granting a narrower role by hand, remember `fields` needs its own entry (or `'*'`) for `read`/`create`/`update` — a grant that only sets `resource`/`action` and leaves `fields` unset is rejected by `validateRolePermissions`, not silently treated as "everything" — and remember `scope: 'any'` if the role should manage more than just what it personally creates.
