```sh
ratchet <command>
```

## `ratchet init`

Scaffolds a ready-to-run project in the current directory. It writes `package.json`, `tsconfig.json`, `ratchet.config.ts`, the starter models and `routes/`, `seed.ts` sample data, `migrations/`, and a `.gitignore`. It also writes the coding-agent guide: `AGENTS.md`, a `CLAUDE.md` that imports it, and `.claude/skills/` (see [Building with a coding agent](/docs/coding-agents)). It never overwrites a file that already exists, so it's safe to re-run.

## `ratchet generate`

Reads `models/**/*.model.ts` and emits, into `generatedDir` (`.ratchet/` by default):

- `schema.ts` — the Drizzle schema
- `validators.ts` — Zod validators
- `registry.ts` — the model registry `ratchet serve` and `ratchet build` read from
- `console-forms.ts` — the [custom console form](/docs/console#custom-forms) registry, one entry per `models/**/*.form.tsx`
- `console-field-inputs.ts` — the [custom field input](/docs/console#custom-field-inputs) registry, one entry per `models/**/*.input.tsx`

It then runs `drizzle-kit generate` to diff the fresh schema against `migrationsDir` (`migrations/` by default) and write any new SQL migration files. Review those files, then apply them with `ratchet migrate`.

Run this any time your models change and you're not using `ratchet dev`.

## `ratchet migrate`

Runs `drizzle-kit migrate` against `migrationsDir` (`migrations/` by default), applying and tracking any pending SQL migration files. It does not touch your models or the schema — run `ratchet generate` first to produce the migration files. Use this for a durable, versioned migration history — the workflow you want outside of local development.

## `ratchet dev`

Watches `models/`, `routes/`, and `seed.ts`. On every change it regenerates, runs `drizzle-kit push` (schema changes go straight to the database, with no migration files), runs `seed.ts`, and restarts the dev server. Each sync runs in a fresh process, so it always reads the files as they are now. If a sync fails, `dev` prints the error with a `fix:` hint, keeps the last good server running, and retries on the next save. Intended for local development only.

<Callout type="warn">
`push` applies destructive changes without asking. Removing or renaming a field drops that column's data. Adding a `required` field with no `default` to a table that already has rows **empties the table**. Use `generate` + `migrate` for any database whose data you need to keep.
</Callout>

## `ratchet seed`

Runs the project's `seed.ts` against the database. `dev` already runs it after every sync. The default export receives `insert` and `isEmpty`:

```ts
import { defineSeed } from '@egig/ratchet/core';
import { Post } from './models/blog/post.model.js';

export default defineSeed(async ({ insert, isEmpty }) => {
  if (await isEmpty(Post)) {
    await insert(Post, { title: 'Hello', status: 'published' });
  }
});
```

`insert(model, values)` validates against the model's create schema (the same rules as `POST /api/:model`) and fails with the field named. It doesn't run the model's `create` pipeline. `isEmpty(model)` guards each block, so re-running never duplicates rows. A missing `seed.ts` is a no-op.

## `ratchet check`

The "is my change OK?" command, for people and coding agents alike. It runs three steps and prints a PASS/FAIL/SKIP line for each:

1. **models**: loads every model and Domain and regenerates `.ratchet/`. No migration files are written.
2. **types**: runs `tsc --noEmit` on the project.
3. **tests**: runs `bun test`, if the project has any `*.test.ts` files.

It exits non-zero if any step fails, so it works in CI too.

## `ratchet serve`

Boots the API server: reads `ratchet.config.ts` and the generated registry, and starts a listening server with the console (`/console` by default — see `consolePath`), `/api/auth/*`, and `/api/:model` mounted. No server entry file needed.

```sh
PORT=3000 ratchet serve   # DATABASE_URL unset -> the local SQLite file
```

## `ratchet build`

Builds the console client (Bun's bundler + Tailwind, hashed assets + manifest) and a bundled server artifact, for deploying without dev tooling at runtime.

## `ratchet studio`

Proxies to `drizzle-kit studio`, for browsing/editing your database directly (SQLite or Postgres — see [Database](/docs/database)).

## `ratchet create-admin`

Creates the root admin user directly against the database, bypassing HTTP entirely. Prompts interactively for an email and password, or accepts `--email`/`--password` for scripted/CI use. Refuses if a root admin already exists.

This is production's bootstrap path: `/api/auth/setup` (and the console's `/setup` screen) 404 unconditionally when `env` resolves to `'production'` (see `FrameworkConfig.env`), so they never reveal whether a root admin exists. In development, `/setup` still works as a normal web flow.

```sh
ratchet create-admin
ratchet create-admin --email admin@example.com --password 'correct horse battery staple'
```
